# Policy Funding OS — Knowledge Base

정책자금 전자책(김팀장 PART 1)과 업종별 승인 케이스 부록을 구조화한 **지식베이스**입니다.
이 폴더는 **앱 UI/라우트/저장 기능과 독립**적이며, 앱 코드에서 import 되지 않습니다(빌드에 영향 없음).
추후 `app/lib/diagnosis.ts` 강화, GPT API / RAG 연결, 프롬프트 컨텍스트 주입에 사용하기 위한 원천 데이터입니다.

## 목적

- 진단·상담·리포트의 **판단 근거**를 코드가 아닌 데이터로 관리한다.
- AI 코치가 실제 상담에서 쓸 수 있을 만큼 **상세하게** 전자책 지식을 보존한다.
- 다음 단계에서 규칙 엔진(diagnosis.ts) 또는 LLM(RAG)로 **그대로 주입**할 수 있게 타입 안정적인 JSON 구조를 유지한다.

## 파일별 역할

| 파일 | 역할 | 주 활용처 |
|---|---|---|
| `funding-playbook.md` | 전자책 전체를 실무 상세 정리(개념·기관전략·준비·탈락원인·사업계획서·실사·로드맵·Q&A·주의사항) | LLM 시스템 프롬프트/RAG 문서, 컨설턴트 참고 |
| `funding-core-principles.json` | 정책자금 / 무상지원금 / 고용지원금 3분류 판단과 트리아지 로직 | 진단 초기 분기, 상담 코치 |
| `funding-agencies.json` | 6개 필수 기관 + 기타 기관의 적합/부적합·자금목적·유리업종·불리조건·순서(먼저/나중)·모드(단독/병행)·상담 멘트·주의 | `diagnosis.ts` 기관 스코어링 강화 |
| `funding-checkpoints.json` | 심사·실사에서 보는 17개 체크포인트(업력·매출·신용·기대출·세금·4대보험·사업장·대표자·업종·고용·인증·특허·연구소·시설·운전·사업계획서·실사) | 진단 폼·고객 상세·리포트 판단 근거 |
| `precheck-rules.json` | 신청 전 제한사항 6가지 + 5대 체크리스트(세금체납 1원=즉시거절) + 90일 사전관리 | 진단 경고 로직, 90일 관리 고객 전환 |
| `rejection-reasons.json` | 탈락 원인 12가지 + 담당자 대응 플레이북 | 리포트·상담 멘트, 재도전 전략 |
| `business-plan-questions.json` | 사업계획서 공통 필수 질문 + 업종별(음식/제조/쇼핑몰/서비스) 질문 | 사업계획서 코칭 |
| `field-review-playbook.json` | 실사/면담 전 체크리스트·예상 질문·약점별 방어 논리 | 실사 대응 코칭 |
| `consulting-contract-notices.json` | 컨설팅 범위 + 계약 전 고지(승인 보장 불가·수수료 시점·환불/연장 등) | 계약 전 안내, 고객 보호 |
| `funding-scripts.json` | 11개 카테고리 상담/클로징/서류요청/반박/사후 멘트 | 고객 상세 메시지 생성, AI 코치 멘트 |
| `funding-upsells.json` | 업셀링 13개 항목 카탈로그(추천조건·멘트·필요자료·연결이유·주의) | 업셀링 추천 |
| `upsell-rules.json` | 업셀링 트리거 규칙(조건 → 추천 항목) + 재접촉 타이밍 | 업셀링 자동 판단 |
| `funding-cases.json` | 부록 **업종별 승인 케이스 64건** 전량 구조화(id·업종·업력·매출·신용·부채·직원·목적·기관·승인액·상황·전략·핵심·리스크·교훈·업셀·출처) | 유사 사례 매칭(현재 `app/lib/cases.ts` 12건의 확장 원천) |

## 데이터 구조 규약

- 모든 JSON은 최상위에 `meta`(title/source/description)를 갖고, 배열형 데이터는 명확한 key 를 가진 객체 배열입니다.
- 기관/업셀 항목은 안정적인 `key`(영문 slug)를 가져 코드에서 참조하기 쉽습니다.
- `funding-cases.json` 의 각 사례는 고정 스키마(18개 필드)를 따르며, 미상 값은 `null` 로 둡니다.

## 앱 연결 로드맵(다음 단계 제안)

1. **규칙 엔진 강화**: `funding-agencies.json` / `funding-checkpoints.json` / `precheck-rules.json` 을 `app/lib/diagnosis.ts` 스코어링·경고 로직에 반영.
2. **사례 확장**: `funding-cases.json`(64건)을 `app/types.ts`의 `ApprovalCase` 스키마로 매핑해 `app/lib/cases.ts`를 확장(현재 12건 → 64건).
3. **멘트/업셀 주입**: `funding-scripts.json` / `funding-upsells.json` / `upsell-rules.json` 을 상담 메시지·업셀 추천에 연결.
4. **LLM/RAG**: `funding-playbook.md` + 각 JSON 을 문서 청크로 임베딩해 GPT API 컨텍스트로 검색 주입.

## 출처 및 주의

- 원천: **김팀장 정책자금 전자책 PART 1 + 보너스 자료(업종별 승인 케이스 DB, p.126~133, 미래경영지원센터)**.
- 케이스는 개별 기업 보호를 위해 업종·지역·금액·업력 등 일부가 유사 범위로 재구성되어 있습니다.
- 정책자금은 같은 업종이라도 업력·신용·체납·기대출·매출흐름·사업장 실체·자금목적에 따라 결과가 달라집니다. 본 데이터는 **정답이 아닌 참고 지도**이며, 승인 여부를 보장하지 않습니다.
